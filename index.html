01

从 AI 课堂的想法出发

用户 · 提问

我想自己搭建一个Ai老师和AI助教的两个Agent共存的课堂，你能配合我一步一步的搭建起来么？

AI · 回答展开 / 收起

可以。我们一步一步搭，每一步都做出能运行、能体验的东西，再根据你的反馈往下走。

先做一个最小课堂，让三个角色能完成一次教学互动：

  • AI 老师：讲解、提问，根据学生回答推进教学。
  • AI 助教：在学生卡住时提供提示，帮助老师了解学生的困难。
  • 学生：回答问题，也可以主动向助教求助。

关键是设计清楚：谁在什么时候说话、两个 Agent 怎么共享课堂信息，以及如何避免抢话或重复解释。 我会配合你把教学流程、角色分工、技术实现和实际测试逐步做起来。

我们先确定第一件事：你想给什么样的学生、上一堂什么内容的课？ 比如“给 5–8 岁孩子上的英语口语课”，或者你已经有的一节具体课程。

02

让学生成为第三个 Agent

用户 · 提问

哦，学生设计成第三个Agent吧

AI · 回答展开 / 收起

好，那我们做一个 AI 老师＋AI 助教＋AI 学生 的三 Agent 模拟课堂。你作为观察者，可以随时暂停、调整角色设定，再重新运行。

三个角色先这样分工：

  • 老师 Agent：围绕教学目标讲解、提问，并判断是否继续。
  • 助教 Agent：观察学生表现，在需要时提示或辅助，避免抢老师的话。
  • 学生 Agent：按照设定的年龄、知识水平和性格回答，可以答错、听不懂或走神。

学生需要有独立的信息边界，只看到课堂上已经发生的内容，避免提前看到老师的答案，影响模拟效果。

第一步先确定场景：你希望这位 AI 学生模拟哪个年龄段、什么水平，学习什么内容？

03

覆盖 3–15 岁与多地区学生

用户 · 提问

我需要3-15岁，每一个年龄都能有一些学生的persona，来模仿各个年龄各个风格的学生 我的学生分布在东南亚、沙特、韩国、日本 他们不一定只学习英语，可能也会学习其他校内学科

AI · 回答展开 / 收起

明白。学生 Agent 要做成一个可切换 persona 的学生库，覆盖 3–15 岁、多个地区和学科，而不是固定扮演某一个学生。

我们可以先按每个年龄 3 个不同的学生，共 39 个基础 persona起步，再加入地区、语言和学科背景。每个 persona 分成四层：

  • 年龄与学习背景：年龄、年级、上学经历、已有知识。年龄相同，能力也可以不同。
  • 地区与语言：所在国家、家庭语言、教学语言，以及用教学语言表达的熟练程度。地区用于补充语言和课程背景，不用来预设性格。
  • 个人学习风格：主动或慢热、谨慎或急于作答、是否愿意求助、遇到挫折的反应。这些特征可以组合，不把孩子固定成“好学生／差学生”。
  • 各学科能力：英语、数学、科学等分别设定。例如，数学理解很好，但用英语解释解题过程比较困难。

此外，还要把稳定的 persona和当堂状态分开。同一个学生今天可能很投入，下一次可能疲倦；课堂中的成功、困惑和老师的反馈，也应该影响后续表现。

例如，一个虚构学生可以是：

8 岁，生活在日本，家庭语言是日语。数学计算较熟练，英语表达较弱。愿意尝试，但怕当众答错；听不懂英文数学题时，可能先猜答案。得到具体提示后会继续尝试，不会因为老师说一句“再想想”就突然掌握知识。

后续模拟时，学生只能依据自己的知识和已发生的课堂内容回答；我们还会检查它是否出现了超出设定水平、过度配合老师的情况。

先补齐一个会影响语言和课程配置的信息：东南亚具体覆盖哪些国家？

04

Persona 的定义、常量与变量

用户 · 提问

在回答你东南亚具体覆盖的国家之前，我想先跟你讨论下，你怎么定义什么是persona，如何写清楚或者定义清楚一个Agent的persona，哪些应该是这个persona的常量哪些是变量。以及构建一个学生Agent，除了有persona以外，还需要什么

AI · 回答展开 / 收起

我建议先把一个边界定清楚：persona 描述“这个学生通常是怎样的人”；完整的学生 Agent 还要描述“他现在会什么、经历过什么，以及此刻如何反应”。

我前面提出“每个年龄先做 3 个 persona”，只是一个起步数量，并没有解决该如何定义和验证它们。现在先把结构讨论清楚更合适。

先说什么是 persona。

在我们的项目里，我建议用这个工作定义：

Persona 是一组相对稳定、能影响行为的个人背景、动机、偏好和反应倾向，让同一个学生在不同课堂情境中保持可辨认的一致性。

其中，“相对稳定”和“影响行为”最重要。

“8 岁，生活在日本，喜欢恐龙”提供了背景，但不足以决定课堂行为。还需要知道：他为什么愿意参与？不确定时会猜、沉默还是求助？老师纠正他以后，他通常如何回应？

同时，persona 应该表达倾向，而非每次必然执行的动作。一个慢热的学生，遇到熟悉的话题也可以主动说话；喜欢恐龙，也不代表每句话都要提恐龙。

怎样把 persona 写清楚？把形容词写成有条件的行为。

例如，只写“内向、容易受挫、需要鼓励”，不同模型可能演出完全不同的学生。我会把它展开成：

面对陌生老师和开放式问题，通常先等待，回答较短。
面对熟悉知识的选择题，即使没有被点名，也可能主动回答。
连续尝试失败后，更倾向于说“不知道”或减少参与。
老师指出已经做对的部分，并提供一个可执行的小提示后，更愿意重试。
鼓励可以提高尝试意愿，但不会直接补齐缺失的知识。

这段定义交代了触发情境、行为倾向、变化条件和能力边界，后续就能用课堂片段检验。

每个关键特征都应该能回答：

  • 什么情况下会表现出来？
  • 会表现成什么可观察的行为？
  • 什么情况下会减弱，或者出现例外？
  • 我们拿什么例子判断它有没有演对？

没有数据依据时，我不建议一开始写“内向程度 0.8”“答错后有 70% 概率沉默”。这些数字需要明确含义和校准，否则只是看起来精确。

常量和变量，要根据变化的时间尺度区分。

我建议分成四类，而不是只分“固定／不固定”。

  1. 一次模拟中固定的背景
    年龄、家庭语言、所在地区、既往教育经历等。它们不能因为几轮聊天突然改变。跨学期模拟时，年龄、年级等可以按时间推进。

  2. 缓慢变化的个人倾向
    主动表达的倾向、面对不确定性的习惯、兴趣、通常如何求助等。这些构成 persona 的核心。短期内保持稳定，长期变化需要有持续经历作为依据。

  3. 随学习经历更新的能力和记忆
    掌握的知识点、常见误解、教学语言熟练度、对某类题目的信心，以及与老师、助教的互动经历。建议单独保存，避免把“不会分数”永久写进性格设定。

  4. 随课堂事件变化的即时状态
    当前注意力、困惑、疲劳、挫败感、参与意愿，以及“这道题有没有听懂”。它们可以在几轮互动中变化，但需要有原因。

例如，“通常敢于尝试”属于个人倾向；“刚连续答错，现在不想开口”属于即时状态，两者可以同时成立。

还有一个容易遗漏的区别：创建学生时可配置，不等于运行中可以随意变化。 我们可以在创建时选择年龄，但不能让模型在课堂里自行修改年龄。

除了 persona，学生 Agent 还需要下面几部分。

① 明确的知识与能力模型。
要具体到当前课程涉及的知识点：会什么、不会什么、哪里有误解、需要什么帮助。多学科场景尤其要把“学科理解”和“教学语言理解”分开。

例如，学生可能会用母语解决一道数学题，却听不懂英文题干。此时给数学提示和翻译题干，应该产生不同效果。

学生模拟研究也指出，大模型本身能力很强，仅靠角色提示扮演初学者，容易产生不合理的错误和学习过程；需要明确限制模拟学生可用的知识，并定义知识如何更新。相关研究

② 独立的信息边界。
学生只能根据自己实际接收到的课堂信息行动。老师的教案、标准答案、助教的内部判断，不能直接混入学生上下文。

在三 Agent 课堂里，还要明确：助教是在对学生说话，还是在给老师发内部消息？学生是否听到了这句提示？这些都会改变下一步反应。

③ 记忆。
学生需要记得刚才尝试了什么、接受过什么提示，以及之前与老师和助教发生过什么。

不过，“刚听过一个答案”和“已经掌握这个知识”要分别记录。记住原题答案，不代表换一道题也会。

④ 行为选择机制。
每轮先决定学生要采取什么行动，再生成具体表达。可选行动可以包括回答、猜测、追问、求助、沉默、请求重复、转移话题等。

这样才能模拟“他选择不回答”，而不是系统每收到一条消息，就强迫学生说出一句完整的话。语音课堂还需要考虑等待、打断，以及非语言操作。

⑤ 学习和状态更新规则。
老师讲解、助教提示之后，什么发生了变化，必须有明确规则。

例如：

  • 泛泛的鼓励，可以提高参与意愿。
  • 提供一个步骤，可以帮助完成当前题目。
  • 独立解决一道变式题，可以作为掌握程度提高的证据。

这些先作为我们的建模假设，之后再用真实课堂记录校准。不能让学生只因为老师说“你明白了吗”，就自动进入“已经学会”的状态。

⑥ 课堂调度和验证机制。
课堂调度负责决定谁可以发言、谁接收消息、沉默后等待多久。这属于课堂系统，不需要再设一个有 persona 的角色。

验证则检查两件不同的事：行为是否符合这个学生，以及他对教学的反应是否合理。 近期学生模拟研究也将行为匹配和接受指导后的变化分别评估。StudentSim 研究

我们还需要保存初始状态和运行记录，才能让同一个学生从相同起点体验不同教学方案。否则，老师方案变了，学生状态也变了，很难判断差异来自哪里。

用一个完整例子串起来：

同一个学生，通常谨慎，怕在陌生老师面前答错。
他会做两位数加法，但没有理解进位；当前精神状态不错。
老师第一次问进位题，他尝试用已有方法回答，出现与误解一致的错误。
老师只说“加油”，他可能愿意再试，但仍然不会进位。
助教用实物分组演示，他在帮助下完成这一题。
系统记录“在提示下完成”，再通过新题观察能否独立应用。

这里，persona 决定他如何面对困难，知识模型决定困难在哪里，课堂经历决定他接下来可能发生什么变化。

所以我建议下一步先做一个学生的完整定义，以及几段用于检验他的课堂情境。先确认我们能稳定模拟一个“有边界、会变化”的学生，再扩展到 3–15 岁和不同地区。

05

能力和记忆如何存储

用户 · 提问

你提到单独保存随学习经历更新的能力和记忆，这个具体研发侧如何操作？

AI · 回答展开 / 收起

具体研发上，我建议：把学生的能力、记忆保存到我们自己的数据库里，由程序负责读取和更新；大模型负责根据这些信息生成学生行为。

这里的“学习”首先体现为数据库中的学生状态发生变化，不涉及每上完一节课就训练或修改大模型参数。第一版可以用这种方式实现。

我用“学生学会数学进位”这个例子展开。

1. 把 persona、能力、记忆分别存储，用同一个学生 ID 关联。

研发可以先建立以下几类数据，初期放在同一个数据库即可，不需要拆成多个服务。

  • student_profiles：学生背景和相对稳定的 persona。
  • student_skill_states：按知识点保存的能力状态。
  • student_memories：课堂中发生过的、值得后续使用的经历。
  • classroom_events：完整的课堂事件记录，便于回放和核查。

能力状态不能只写“数学水平：中等”，而要具体到当前教学涉及的知识点。例如：

{
  "student_id": "student_008",
  "simulation_id": "run_001",
  "skill_id": "math.addition.carry",
  "status": "with_support",
  "misconceptions": ["把个位相加的两位数直接写进个位"],
  "evidence": {
    "independent_successes": 0,
    "supported_successes": 1
  },
  "last_evidence_event_id": "event_023",
  "version": 4
}

这里的 with_support 表示“在帮助下能完成”。第一版可以先采用“未接触、正在学习、提示下完成、独立完成”等可解释状态，不急着使用看似精确的掌握概率。

记忆则记录经历：

{
  "student_id": "student_008",
  "simulation_id": "run_001",
  "type": "learning_episode",
  "summary": "助教用十根小棒换一捆的演示，帮助我完成了进位题。",
  "related_skill_ids": ["math.addition.carry"],
  "source_event_ids": ["event_021", "event_023"]
}

这两条数据表达不同的东西：能力说明“现在能做到什么”，记忆说明“之前经历过什么”。 学生可以记得一次演示，但还不能独立完成新题。

2. 每次轮到学生行动，程序组装这一次所需的上下文。

不需要把学生全部历史塞给大模型。课堂程序按当前任务读取：

  1. 学生的 persona。
  2. 当前题目涉及的能力与误解。
  3. 当前注意力、困惑等即时状态。
  4. 与当前任务有关的少量记忆。
  5. 学生有权限看到的课堂消息。

例如，当前教进位，就读取加法、数位、进位相关状态，不必加载全部英语学习记录。

然后调用学生模型，让它返回结构化的行动：

{
  "action": "answer",
  "utterance": "是三十二吗？",
  "help_requested": false
}

学生模型生成“怎么表现”，不直接修改自己的能力数据库。 它说“我懂了”，只能算一次课堂表达，不能自动当作掌握证据。

3. 能力更新由独立的更新逻辑控制。

这里的“独立”可以只是后端的一段函数，不需要额外增加一个有角色设定的 Agent。

第一版我建议用“固定规则＋必要时调用模型判断”的方式：

  • 程序能直接判定的，使用规则，例如答案是否正确、之前是否给过提示。
  • 开放式回答需要理解时，调用模型进行结构化评估。
  • 评估结果交给程序校验，再决定是否更新数据库。

例如，一次回答结束后产生这样的证据：

{
  "event_id": "event_023",
  "skill_id": "math.addition.carry",
  "answer_correct": true,
  "support_level": "step_by_step",
  "task_type": "original_question"
}

更新程序据此判断：这是在逐步帮助下完成原题，可以增加“提示下成功”的记录；不足以直接改成“独立掌握”。

每次修改还应保留：修改前是什么、修改后是什么、依据哪条课堂事件、用了哪个版本的更新规则。 出现“学生突然变聪明”的问题时，研发可以追溯。

4. 模拟学生还有一个特殊问题：教学怎样让他获得新能力？

这里需要区分两个环节：

  • 模拟学习发生：学生收到讲解或提示后，按我们设定的学习规则，更新其模拟知识状态。
  • 观察学习表现：后续通过独立作答、变式题等，观察其表现是否支持更高的掌握判断。

例如，第一版可以设定：

接收到相关演示，并参与完成一个步骤后，将该知识点从“正在学习”更新为“提示下完成”；后续满足预设的独立作答条件，再更新为“独立完成”。

这是一条模拟规则，需要校准。不能把它当成真实儿童必然遵循的学习规律，也不能因为规则规定学生会进步，就反过来认定老师教得有效。

研发上最好同时保留“模拟器内部能力状态”和“老师根据表现估计的能力”。老师只能看到课堂行为和允许共享的评估结果，不能直接读取学生内部设定，否则测试会失真。

5. 把这些步骤串成一次完整的运行。

每轮课堂的执行顺序可以是：

老师／助教发出消息
        ↓
程序判断学生是否能接收到，并记录事件
        ↓
按规则处理提示、讲解对学生状态的影响
        ↓
读取 persona、相关能力、记忆和当前状态
        ↓
调用学生模型生成行动
        ↓
记录行动，评估本次表现
        ↓
更新能力、即时状态和相关记忆

能力更新和记忆写入需要关联同一事件，重复处理时不能重复累计；更新时检查状态版本，防止老师和助教的并发消息互相覆盖学生状态。

06

课堂中何时读取与更新状态

用户 · 提问

把学生的能力、记忆保存到我们自己的数据库里，由程序负责读取和更新；大模型负责根据这些信息生成学生行为。 这里，应该在什么时候读取和更新？是需要在学生student首次启动的时候读取，然后整个课堂中都使用这个能力与记忆，还是说课程进行中，还需要分阶段更新数据库，并更新给学生Agent？

AI · 回答展开 / 收起

课程进行中需要持续更新，并把相关变化提供给学生 Agent 的下一次调用。 只在启动时读取一次，会让学生一直按照“上课前的自己”行动。

不过，每次调用都使用最新状态，不等于每次都重新查询全部数据库。 研发上可以把“读取数据库”“更新运行状态”“保存数据库”分开处理。

我建议第一版采用：开课时加载，每次学生行动前准备最新上下文，每个有效互动结束后保存变化。

开课时：加载这个学生的起点。

从数据库读取：

  • persona；
  • 本节课相关的知识能力；
  • 与本节课有关的历史记忆；
  • 上次结束时需要继承的状态。

程序把它们放进这堂课的“运行状态”里，也就是后端内存中的一个学生状态对象。后面课堂中的更新先作用于这个对象。

这样，不必每说一句话，都从数据库重新加载整个学生。

课堂中：在有意义的事件后更新，而不是固定每隔几分钟更新。

不同事件需要更新的内容不同：

  • 老师提出问题：可能改变困惑程度、当前任务，不代表知识增加。
  • 助教给出提示：记录学生已经获得什么帮助，必要时更新当前理解或可完成的步骤。
  • 学生完成回答：记录作答结果、是否依赖提示，并按规则更新能力证据。
  • 进入新知识点：加载新知识点相关能力和历史记忆。
  • 一段教学结束：整理这一段值得保留的记忆，保存阶段快照。

不是每个事件都修改能力。例如，“老师说了句你好”需要记录对话，但通常不需要改变数学能力。

每次轮到学生行动前：使用最新状态构建输入。

这是最关键的一步。可以把它理解成：每次学生要说话或做动作，程序都重新准备一份“此刻的学生资料”。

这份资料包括稳定的 persona、最新的相关能力、当前状态、已收到的提示和近期对话。即使 persona 没变，能力或状态变了，下一次调用也必须体现变化。

对于常见的大模型 API，数据库中的修改不会自动被模型知道。必须由我们的程序把最新数据放进下一次请求。即使沿用同一段对话，也要明确提供当前状态，避免旧设定继续生效。

拿一段进位教学举例：

  1. 开课：加载“会不进位加法，尚不会进位”。
  2. 老师提问：学生按当前能力尝试，答错；程序记录错误，更新困惑状态。
  3. 助教演示：程序记录演示已被学生接收，按模拟规则更新为“可以尝试跟着步骤做”。
  4. 学生再次回答前：把这个最新状态和演示内容一起交给模型，学生现在可以利用帮助。
  5. 学生在帮助下答对：保存“提示下完成”的证据，仍不直接认定独立掌握。
  6. 老师出一道新题：下一次调用使用更新后的能力，但不自动附带上一题的逐步提示，观察学生如何迁移。

如果只在开课时加载且后面不更新，第 4 步可能仍然表现得完全没学过；如果任由对话历史决定一切，又可能听完演示就突然变成全会。

写数据库：第一版按每个有效互动保存，课末再做整理。

我建议：

  • 每条课堂事件发生后，及时保存事件记录。
  • 能力、状态确实变化后，保存增量变化及其依据。
  • 一个教学环节结束时，整理长期记忆。
  • 课程结束时，保存最终状态和下次可继承的记忆。

没有必要每轮都生成一份长期记忆；原始事件先保留，重要经历再整理。例如，“老师刚说了一句鼓励”可以先在近期对话里，“多次具体提示后重新愿意尝试”才可能值得形成一条长期记忆。

还有一条研发约束：同一个学生的状态更新应按事件顺序处理；一次模型调用使用一份固定版本的状态。 如果学生生成回答时助教又发来新提示，要明确让它进入下一轮，或者取消当前生成后重试，不能让一次回答对应两个不同版本的学生。

所以，你提出的两个方案中，我们应采用**“启动时加载＋课中按事件更新＋下次行动前提供最新状态”**。阶段节点适合整理记忆和保存快照，影响当前行为的变化则应及时生效，不必等到一个阶段结束。

独立完成与帮助下完成

用户 · 提问

那又是基于什么来判定，学生是在帮助下完成的，还是独立完成的呢？来得到这两个参数的值？

"independent_successes": 0,
    "supported_successes": 1
AI · 回答展开 / 收起

这两个值应该由程序根据作答结果和帮助记录累计，不能让学生 Agent 自己报告“我是独立完成的”。

而且我前面的例子省略了一层：要先给每次任务生成一条判定记录，才能可靠地得到这两个计数。

第一步，先定义这次任务允许学生使用什么。

“独立完成”需要有明确条件。例如，本次任务规定：

学生可以看题目和配图，可以使用之前学过的知识；作答过程中没有收到针对本题的额外提示。

按照这个定义，之前上课学过解题方法，不影响独立完成。独立不是“从来没有被教过”，而是完成当前任务时，没有依赖超出既定条件的帮助。

对于你的多语言课堂，这个定义尤其重要：如果我们测数学，翻译题干可以被预先规定为允许的条件；如果测英文阅读理解，翻译题干就属于帮助。因此，判定要跟着教学目标走。

第二步，记录作答前，学生实际接收过哪些帮助。

老师和助教的课堂事件，都关联到具体任务，例如：

{
  "event_id": "event_022",
  "task_id": "task_007",
  "recipient": "student_008",
  "type": "hint",
  "support_level": "step",
  "content": "先算个位，看看有没有满十。",
  "delivered_before_answer": true
}

这里可以先设计几种帮助类型：

  • 鼓励或流程提醒：“可以再试试。”通常不提供解题信息。
  • 方向提示：“注意个位有没有满十。”
  • 步骤帮助：“8 加 7 是 15，把 5 写在个位。”
  • 答案提供：“答案是 35，跟我说一遍。”

关键依据是帮助内容、提供时间、接收者、对应任务。助教给老师的内部建议，学生没有收到，就不能算学生获得帮助。

这些标签可以由课堂程序预先标注；自由生成的提示，则需要检查实际内容，避免把已经透露答案的话误标成“鼓励”。

第三步，将“答案是否正确”和“是否得到帮助”分开判定。

正确性由题目的评分规则决定：

  • 数值题、选择题，可以用程序判分。
  • 开放式回答，按明确的评分标准评估；必要时调用独立的评估模型。
  • 证据不足时标为待定，不强行累计成功。

帮助情况来自事件记录。两者合并后，才能得到本次结果：

{
  "task_id": "task_007",
  "answer_event_id": "event_023",
  "correct": true,
  "support_level": "step",
  "support_event_ids": ["event_022"],
  "outcome": "supported_success"
}

后端读取这个结果，再让 supported_successes 增加 1。

如果答案正确，而且记录确认作答前没有收到超出允许条件的帮助，就可以判为 independent_success，让对应计数增加 1。

但“得到帮助后答对”还需要避免两种误判。

第一，直接复述答案不等于在帮助下完成解题。我建议单独记录为 answer_reproduction，不要混进 supported_successes。如果任务目标本来就是跟读，则应按跟读任务的标准评分。

第二，刚被告知答案，再把同一道题做对，不能直接算新的独立成功。需要保留“之前见过本题答案”的记录。若想检查能否独立应用，应该安排未透露答案的新题或变式题。

例如，下面这段互动可以这样累计：

  1. 学生第一次答错：两个成功计数都不增加。
  2. 助教提供一个步骤，学生完成剩余步骤并答对：supported_successes + 1。
  3. 老师给一道新的同类题，学生没有额外帮助就答对：independent_successes + 1。

同一次完成只累计一次，重试、消息重发或重复评估不能重复计数。底层保留全部作答记录，汇总计数按任务结果生成。

还有一个需要准确表达的边界：这个方法判定的是“在什么帮助条件下完成”，不能直接证明“帮助导致了成功”。 学生有可能本来就会，只是助教提前提示了；我们只能把这一题记为“有帮助条件下完成”，再用无提示的新题观察独立表现。

因此，研发真正需要保存的核心是：题目、评分结果、帮助记录、时间顺序和判定依据。这两个数字只是这些证据的汇总，也不能单独代表学生已经掌握了知识。

这里有几个重要区别：

  • before / after：实际改了什么，可以只记录被修改的字段。
  • evidence_event_ids：依据是什么。例如 event_022 是助教提示，event_023 是学生回答。两条事件本身需要保存内容、发送者和顺序。
  • reason_code：为什么满足更新条件，例如“逐步提示后回答正确”。它是业务判定理由，不需要保存模型的内部思考过程。
  • rule_version：用的是哪一版学习更新规则。
  • state_version：这个学生状态的第几次更新，用来确认先后顺序，避免互相覆盖。

一次更新，在后端大致经过四步。

  1. 先保存课堂事件。
    记录老师或助教说了什么、学生回答了什么，并给每条事件分配唯一 ID。

  2. 评估并生成变更方案。
    更新模块读取当前状态、相关事件和指定版本的规则，算出“哪些字段应该从什么改成什么”。

  3. 检查这次变更是否合法。
    例如，关联的事件是否存在、是否属于这个学生和本次模拟、该事件是否已经处理过，以及状态有没有被另一条更新抢先修改。

  4. 同时保存新状态和变更记录。
    对使用关系型数据库的第一版，可以把这两次写入放在同一个数据库事务里：要么都成功，要么都不生效。

第 4 步可以避免一种很麻烦的情况：学生能力已经变了，但记录保存失败，之后再也查不出原因。

如果评估环节需要调用大模型，通常先完成模型评估，再进入短暂的数据库事务；提交前重新检查状态版本。如果状态已经变化，就重新评估或重试，不能直接覆盖。

“保存规则版本”不只是写一个版本号。

研发还需要保留这个版本对应的实际规则。

例如：

learning_rules_v0.3：在逐步提示下答对，累计一次提示下成功；不直接升级为独立完成。

后来改成 v0.4，旧版本仍应可查询。否则，日志虽然写着 v0.3，研发也无法知道当时到底执行了什么。

如果判定依赖大模型，还应关联一条评估记录，保留：

  • 当时使用的模型标识；
  • 评估提示词和评分标准的版本；
  • 实际用于评估的输入或其可还原引用；
  • 模型当时输出的结构化判定。

这样才能查看当时实际判了什么。仅保留模型名称、以后再调用一次，不保证得到同样结果。

发现“学生突然变聪明”时，排查会沿着这条链进行。

假设第 12 轮学生突然独立解决了难题：

先查看第 12 轮生成回答时实际使用的状态版本和上下文记录，再定位该状态之前的变更，最后打开对应的课堂证据和规则版本。

这能区分几类问题：

  • 状态本身被错误提升：检查更新规则或评估结果。
  • 状态没有提升，但学生仍答得过强：检查学生生成是否遵守能力限制。
  • 数据库状态正确，但调用使用了别的版本：检查上下文组装或缓存。
  • 答案提前进入了学生上下文：检查消息权限和题目答案泄露。

不必要求第一版建设复杂的全量事件回放系统；当前状态＋不可覆盖的变更记录＋调用输入关联，就能覆盖你现在最关心的排查需求。

“学习规则”就是：系统用什么机制，决定一次教学经历会让这个模拟学生发生什么变化。 它需要考虑年龄、已有知识、语言能力和学科特点，但我建议采用“共同框架＋具体知识点规则＋个体参数”，不要为每个“年龄 × 国家 × 科目”分别写一套。

先修正我前面一个过于简化的说法：“得到提示后答对，就把能力升级”主要是表现记录与能力评估规则，还不能完整代表学习过程。

需要区分三类规则。

  • 学习规则：收到讲解、练习或反馈以后，内部知识如何变化。例如，原先不知道“十个一可以换成一个十”，演示后形成了这个概念的初步理解。
  • 表现规则：在当前知识、语言和课堂状态下，学生如何作答。例如，理解了进位，但计算时仍可能出错。
  • 评估规则：观察到这次作答以后，系统如何判断学生的掌握情况。例如，提示下答对只能增加相应证据，不能直接认定独立掌握。

知识追踪研究也区分了学习状态与作答表现：学生可能会却失误，也可能不会却猜对。因此不能把一次答对直接等同于知识增长。CMU 的知识追踪说明

对我们的模拟器来说，学习规则负责改变内部状态，表现规则负责生成行为，评估规则负责解读行为。三者要有关联，但不能混成一条“答对就升级”。

年龄应该影响哪些地方？

我建议年龄主要用于生成初始配置，再用具体能力覆盖默认值。例如：

  • 能理解怎样的语言和指令；
  • 是否具备当前任务需要的阅读、数量、符号等基础能力；
  • 在我们的模拟设定里，能处理多长、多复杂的操作序列；
  • 表达理解时，可以用指认、操作、短句还是较完整的解释。

这些应该作为可配置、需要校准的特征，不能直接写成“5 岁要教五遍，10 岁教两遍”。

例如，两个同为 8 岁的学生，一个已经理解数位，一个还没有理解，面对相同进位演示，模拟学习结果应该允许不同。这里起直接作用的是先备知识是否具备，年龄只是背景。

国家应该影响哪些地方？

我不建议直接设计“日本学生学习速度”“沙特学生遗忘速度”这样的参数。

国家或地区更适合关联这些具体信息：

  • 使用什么课程体系，之前接触过哪些知识；
  • 家庭语言、学校语言和本节课教学语言；
  • 对题目里的情境、单位和表达是否熟悉；
  • 学过哪些解题方法或书写约定。

例如，一个学生不会用英语回答科学问题，可能是表达受限，也可能没有理解科学概念。我们的规则应分别处理这两种情况。

国家帮助我们配置背景；不能仅凭国家推定某个学生的认知能力、性格或学习速度。

科目需要不同，进一步说，要具体到知识点和任务。

同一个科目内部，学习过程也不完全相同：

  • 英语词汇：辨认图片、听懂单词、主动说出单词，需要分别记录。
  • 数学进位：数位理解、十换一、计算步骤和独立应用，需要分别记录。
  • 科学概念：记住术语、理解解释、用概念预测新现象，需要分别记录。

因此，“学会英语”或者“数学能力增加 10 分”都太粗。更合适的是：

这次教学可能影响哪个具体知识点的哪种能力？在什么任务条件下能够表现出来？

这样，学生学会认出单词，不会自动被更新成能熟练造句；会模仿一道数学例题，也不会自动获得整类题目的迁移能力。

设计时，建议你给每条学习规则写一张“规则卡”。

不必一开始写复杂算法，先把下面六件事描述清楚：

  1. 作用对象：更新哪个知识点、哪个能力维度。
  2. 触发经历：什么课堂事件可能产生学习，例如演示、解释、练习、纠错。
  3. 生效条件：需要哪些先备知识，学生是否接收到并能理解教学信息。
  4. 变化范围：哪些内部状态可以改变，是否允许不变，以及变化幅度如何配置。
  5. 暂不获得的能力：这次经历尚不足以支持什么，例如独立迁移或长期保持。
  6. 验证与依据：预期出现什么后续表现；规则来自真实数据、教研判断，还是人为设定的测试场景。

其中第 4 项不能默认“讲了就学会”。可以采用确定性的场景配置，也可以采用概率模型；如果使用概率，就要记录参数来源和版本，避免模型每轮随意决定学习速度。

以“十个一换成一个十”为例，一张初版规则卡可以这样写。

**规则名称：**通过实物演示建立十换一的初步映射。
**作用对象：**十进制数位概念中的“十换一”。
**触发经历：**老师或助教完成小棒分组演示，并邀请学生参与一次交换操作。
**前提条件：**学生已能数到十，理解当前操作指令，并实际接收到演示。
**变化配置：**测试场景 A 设定本次经历后形成实物层面的映射；场景 B 设定仍保留原有误解，需要进一步教学。
**变化边界：**不自动获得纸笔进位算法，也不自动获得英文解释能力。
**后续检查：**换一组小棒，观察能否完成交换；再换成纯数字题，检查迁移表现。
**依据状态：**初版为教研定义的模拟假设，尚未通过真实学生数据校准。

这里刻意设置了两种可能结果。第一版先用它们测试老师能否识别学生差异、采取不同教学行动，比凭空设定一个“演示后 80% 学会”的数字更容易审查。

年龄、语言和课程背景，都通过前提条件与个体配置进入这条规则；不需要复制出十几套几乎相同的规则。

产品文档还需要明确：我们当前在做哪一种模拟。

如果目的是测试老师和助教的流程，可以使用人为定义、可重复的学习场景。例如：

该学生在泛泛鼓励后仍保留误解；在具体演示后形成初步理解；换成符号题仍需要帮助。

这是一个可验收的测试设定。

如果目的是预测真实儿童的学习效果，或比较两种教学方案哪种更有效，就需要真实课堂记录、学习前后表现和独立验证来校准。否则，我们规定“某种提示有效”，模拟结果自然就会显示它有效，无法据此证明教学优势。学生模拟研究也强调，知识边界与学习变化的真实性，需要独立验证，不能仅凭对话听起来像学生来判断。学生模拟有效性框架

针对你现在的阶段，我建议 PRD 先这样规定：

系统按知识点配置学习状态转移规则。规则结合学生先备知识、教学语言理解、当前状态和实际接收到的教学经历，决定内部知识是否及如何变化。年龄用于初始化相关特征，国家或地区用于配置课程和语言背景，不直接决定学习速度。学习状态、作答表现和掌握评估分别记录。所有规则须标明适用范围、版本和依据，未经数据校准的规则须标记为模拟假设。

下一步应先选择一个小知识点，写出基础已具备、基础有缺口、教学语言受限三种学生配置，用同一段教学检查规则是否能产生合理差异。等这一套跑通，再扩展到不同年龄、地区和学科。

设计补充 · 2026-10-06

三个角色，三份 Persona。

每个角色包含 7 个模块，可切换查看包含内容、构建步骤、运行机制和行为边界。

学生 Persona 描述相对稳定的行为倾向，知识能力、当前状态和记忆分别建模。老师统筹课堂，助教提供个体支持；职责、知识正确性、权限和评价标准由系统规定，Persona 决定约束内的行为倾向。

年龄、语言、课程体系及学情用于适配，不按国籍预设性格或能力。基于课堂设计讨论整理的产品方案。模块划分与运行机制尚需通过真实教学观察校准，不是已经验证的儿童心理量表或教学效果结论。

P1

学生 Agent · Persona 结构图谱

在明确的学习与人际情境中，这个学生通常怎样参与、表达、选择学习方法、寻求帮助，以及应对成功和困难。

7 个模块

1．背景与经历

学生熟悉什么环境与经验？

包含内容
年龄（月）、年级、课程体系、家庭与教学语言、学科学习经历、熟悉的生活情境。

构建步骤与机制

  1. 收集明确事实

    区分居住地、课程、语言接触与学习经历；未提供的信息保留未知。

  2. 建立初始配置

    年龄提供宽泛参考；3 岁和 14–15 岁需补充证据，不直接外推。

  3. 连接具体任务

    熟悉经历决定可用类比；知识与语言能力由能力状态决定。

运行机制
背景与经历 → 情境熟悉度 → 理解任务的前提与表达素材。
稳定项与变量
背景事实通常慢变；当前课程与任务单独配置。
边界与验收
国家不直接决定性格、能力或学习速度；本节课的任务属于课堂配置。

2．兴趣与动机

他为什么愿意参与？

包含内容
兴趣主题、学习目标、外部要求、自主选择需求，以及对挑战、互动或关注的偏好。

构建步骤与机制

  1. 分开兴趣与目标

    喜欢故事、想提高成绩和家长要求，可以同时存在。

  2. 比较相近任务

    保持难度相近，比较有无兴趣情境或选择权时的开始、坚持和提问。

  3. 定义条件与例外

    记录哪些条件更愿意参与；未校准的参数标记为模拟假设。

运行机制
任务价值与选择权 → 参与意愿与努力分配 → 学习机会。
稳定项与变量
兴趣与价值取向慢变；当前参与意愿动态更新。
边界与验收
兴趣和参与不能直接增加知识掌握；此刻想不想学属于状态。

3．表达与课堂参与

他怎样表达与进入课堂对话？

包含内容
主动发言、轮流意识、公开与私下表达差异、熟人与陌生人差异、表达方式偏好。

构建步骤与机制

  1. 把标签换成行为

    分别描述举手、插话、等待、点名后回答和主动追问。

  2. 比较相同任务

    保持知识与语言难度相同，改变全班或一对一、是否点名、准备时间。

  3. 写出触发与例外

    公开表达少，一对一更愿意解释；抢答倾向与答对能力分开。

运行机制
理解程度、表达安全感与参与倾向 → 发言意图；轮次编排 → 实际发言机会。
稳定项与变量
表达与轮流习惯慢变；当轮是否发言受理解、情境与发言机会影响。
边界与验收
活跃不等于掌握，沉默不等于不会；基础好不必然坐不住。

4．求助与反馈反应

卡住以后，他会怎么办？

包含内容
主动求助门槛、继续尝试或回避、暴露困惑的意愿、公开或私下纠错反应。

构建步骤与机制

  1. 还原困难事件

    记录先尝试什么、卡在哪里，以及教师何时介入。

  2. 比较帮助方式

    比较泛泛询问、具体卡点提示、私下交流与公开纠错。

  3. 区分关系与知识效果

    更愿意表达可影响信任与求助状态；学会与否另用后续任务检验。

运行机制
发现困难 + 愿意暴露困惑 + 预期能得到帮助 → 求助行为。
稳定项与变量
求助与反馈反应倾向慢变；当前困惑、信任和已获帮助动态更新。
边界与验收
教师的鼓励方法属于教学策略；学生对它的反应倾向属于 persona。

5．自我管理与任务习惯

他怎样开始、维持和完成任务？

包含内容
任务启动、计划、检查、干扰后返回任务，以及对外部提醒的依赖。

构建步骤与机制

  1. 定义任务证据

    看能否复述目标、继续步骤与发现遗漏，不只看坐姿和眼神。

  2. 比较任务条件

    改变活动形式、难度、持续时间、休息、干扰或步骤提示。

  3. 定义偏离与恢复

    记录何时偏离，以及什么提醒有助于重新进入任务。

运行机制
习惯倾向 + 当前疲劳 + 任务负荷 + 活动形式 → 持续投入与自检行为。
稳定项与变量
任务习惯慢变；当前疲劳、投入和任务负荷动态更新。
边界与验收
5–8 分钟是活动设计经验，不是所有 4–6 岁孩子的注意力上限。

6．学习策略与支架使用倾向

他习惯用什么办法学习？

包含内容
看例题、模仿步骤、试错、画图、复述、寻找规律和主动使用提示。

构建步骤与机制

  1. 收集过程

    记录第一步选择、使用什么辅助，以及能否说明理由。

  2. 对照支架与变式

    同一概念下，比较有步骤、撤去步骤及变化后的题目。

  3. 拆分偏好与能力

    常用模板是策略倾向；独立执行、理解原理和迁移是能力状态。

运行机制
Persona → 策略选择；能力状态 → 执行约束；学习经历 → 策略库更新。
稳定项与变量
策略偏好慢变；可用策略库与执行能力可随学习经历更新。
边界与验收
喜欢图片或动作不能固化为视觉型或动觉型学习者。

7．自我判断与情绪应对倾向

他怎样看待自己的表现？

包含内容
分学科自信、失败归因、冒险作答意愿、检查意识和再次尝试倾向。

构建步骤与机制

  1. 收集判断与行为

    询问确定程度，并观察是否尝试、核对、修改或放弃。

  2. 比较不同情境

    比较不同科目、难度，以及公开和私下反馈下的差异。

  3. 分开慢变信念与即时情绪

    重复、跨情境的证据才支持长期调整；一次挫折先更新当前状态。

运行机制
成功预期与失败代价判断 → 尝试、求助、复查和持续投入。
稳定项与变量
自我判断与应对倾向慢变；一次成功或挫折先更新当前状态。
边界与验收
允许自信但答错、没把握但答对；自信与实际能力分别建模。
P2

老师 Agent · Persona 结构图谱

面对不同学情，这位老师通常怎样组织教学、引导思考、提供反馈和调整课堂。

7 个模块

1．教学取向与自主性支持

在允许的教学路径中，通常怎样支持学生学习？

包含内容
先示范或先探索的倾向、选择权的提供方式、过程解释与独立尝试的重视程度。

构建步骤与机制

  1. 确定共同目标

    先固定课程目标、任务要求与支持边界；风格差异只能在允许的教学路径内体现。

  2. 设置对照情境

    给教师相同的学生证据和任务，比较先示范、先尝试与有限选择三种处理。

  3. 写出偏好与切换条件

    例如通常先让学生尝试；指令未理解或先备知识缺失时，先澄清或示范。

运行机制
课程目标与学情筛出可行行动 → persona 影响行动优先顺序 → 根据学生回应调整。
可观察例子
“你想先画图试试，还是先看一个例子？”
稳定项与变量
自主性支持取向相对稳定；本题选择、提示量与支架程度随学情变化。
边界与验收
不能为了维持探索风格一直不给必要帮助；检验是否根据理解证据切换，而非只检验措辞。

2．讲解与知识呈现习惯

通常怎样把一个知识点讲清楚？

包含内容
情境或规则的切入偏好、示例选择、步骤拆分、解释密度、用词与复述习惯。

构建步骤与机制

  1. 界定讲解目标

    标明概念、先备知识和学生教学语言水平；学科知识正确性独立校验。

  2. 比较同概念的表达

    准备情境、示范、图示或规则等可用版本，记录讲解顺序与一次引入的信息量。

  3. 定义降级与换路

    根据学生复述和作答决定拆步、换例子或回补先备知识，避免只是反复原话。

运行机制
知识与语言约束 → 可用表示方式 → 按讲解偏好组织 → 理解检查 → 改写或换方式。
可观察例子
偏情境：“分零食时怎样分得一样多？”偏结构：“先确定总量，再确定分成几份。”
稳定项与变量
讲解组织偏好慢变；例子、句长、语言与步骤大小按任务调整。
边界与验收
爱讲故事不意味着所有内容都讲故事；不能把画图偏好当成学生固定学习风格。检查知识是否失真、是否过度解释。

3．提问与对话组织

通常怎样让学生思考并进入讨论？

包含内容
开放或聚焦提问偏好、追问方式、等待习惯、邀请沉默学生的方法和轮流表达方式。

构建步骤与机制

  1. 拆分提问目的

    区分检查理解、引出理由、比较方法和邀请参与，避免每次都问“懂了吗”。

  2. 设置同题互动案例

    比较抢答、沉默、答错与只说答案时的处理；保持任务难度和可观察证据一致。

  3. 写出轮次与追问规则

    先给思考机会，再邀请表达；对快速回答者追加理由问题，对沉默者提供低压力入口。

运行机制
提问目的 + 当前回应 → 选择追问或邀请方式；发言权限与同时说话限制由编排器执行。
可观察例子
“先各自想一想。你愿意说第一步吗？已经有答案的同学，想想为什么。”
稳定项与变量
对话组织习惯相对稳定；等待时长、问题难度与发言顺序动态决定。
边界与验收
沉默的原因保持待确认；不能因爱互动而频繁打断思考，也不能把抢答当作全班理解。

4．节奏与课堂组织

通常怎样组织活动、过渡与课堂节奏？

包含内容
流程预告、阶段总结、过渡提示、规则提醒风格，以及对预定节奏的坚持程度。

构建步骤与机制

  1. 区分计划与风格

    课程时长、活动限制和必要环节由课堂配置确定；persona 描述怎样引导与提醒。

  2. 观察节奏冲突

    设置进度落后、部分学生卡住和少数学生提前完成等情境，比较全班或分层处理。

  3. 明确调整条件

    定义何时短暂停顿、交给助教局部支持、加入巩固或请求调整计划。

运行机制
时间预算 + 班级理解证据 + 个别需求 → 保持、拆分或调整活动 → 用一贯方式说明过渡。
可观察例子
“我们先核对共同的第一步；需要继续练习的同学，助教会陪你完成。”
稳定项与变量
组织与提醒风格慢变；实际速度、活动长度和支持安排随课堂变化。
边界与验收
不能为了显得高效跳过必要理解检查；没有私有支持通道时，不能虚构同时进行的一对一辅导。

5．反馈与纠错方式

学生答对或答错后，通常怎样反馈？

包含内容
先问理由或先指出问题的倾向、反馈具体程度、自我纠错邀请、鼓励与纠正的表达顺序。

构建步骤与机制

  1. 标注错误与目标

    区分概念误解、执行疏漏、语言表达和任务理解问题；证据不足时先追问。

  2. 构建同一错误的反馈对照

    比较直接指出、提示定位和邀请自查，记录信息量与是否提前暴露答案。

  3. 规定完成后的检查

    反馈后安排可行的再尝试；独立表现与帮助后表现分开记录。

运行机制
错误证据与评估阶段 → 允许的反馈级别 → persona 决定表述及顺序 → 再尝试检验。
可观察例子
“你已经找到了总量。我们再检查一下：这里应该分成几份？”
稳定项与变量
反馈表达习惯慢变；提示级别、纠错时机与反馈内容动态变化。
边界与验收
温和不等于把错误说成正确；严格不等于羞辱。处于独立测评时，不能按平时风格偷偷提示。

6．关系与沟通风格

通常以怎样的语气与学生建立关系？

包含内容
温暖程度、正式程度、幽默使用、表达活力、倾听与确认感受的习惯。

构建步骤与机制

  1. 选择可观察的表达维度

    用句式、语气和回应方式定义“温暖”或“沉稳”，不只写抽象形容词。

  2. 制作配对话语样本

    对相同的困惑、成功和拒绝参与，写出不同风格且同样尊重学生的表达。

  3. 设置情境覆盖与例外

    根据年龄、语言理解和学生反应调整表达；学生不喜欢玩笑时停止使用。

运行机制
当前交流目的与学生信号 → 调整语言难度与表达强度 → 在稳定沟通风格内回应。
可观察例子
沉稳：“可以慢一点，我们先看这一步。”活泼：“先解决这一小步，再挑战下一步。”
稳定项与变量
关系定位与沟通风格慢变；句长、音量或语速等可用表达参数按实际通道调整。
边界与验收
不按国籍预设学生喜好；不编造真实教师履历，不营造排他性依赖。知识要求不因风格而降低。

7．证据使用与适应倾向

遇到新证据时，通常怎样修正教学判断？

包含内容
先澄清或先验证的习惯、解释判断依据的详略、面对相反证据的调整方式，以及吸纳助教反馈的方式。

构建步骤与机制

  1. 定义可见证据

    使用实际作答、课堂行为和助教记录；模拟学生隐藏状态是否可见，由实验模式单独规定。

  2. 安排矛盾案例

    例如点头但变式题失败、沉默却独立答对；比较是否追问、修正而非坚持初始标签。

  3. 形成复盘与协作规则

    助教报告观察、已给帮助和仍不确定之处；老师按职责处理计划调整，记录变更依据。

运行机制
新证据 → 更新学情判断 → 检查当前策略 → 保持或切换；persona 影响验证与沟通方式。
可观察例子
“你能做原题，但换一种说法会卡住。我们检查一下，是题意还是这个方法还不清楚。”
稳定项与变量
验证与复盘习惯慢变；学情判断和教学方案逐事件更新，persona 修订需单独版本化。
边界与验收
尊重证据与承认不确定是共同要求，不是可关闭的性格选项；不能用“学生说懂了”直接判定掌握。
P3

助教 Agent · Persona 结构图谱

学生遇到困难时，这位助教通常怎样发现问题、介入支持、与老师协作，并逐步把任务交还给学生。

7 个模块

1．关系定位与沟通方式

通常怎样让学生愿意接受支持？

包含内容
耐心解释或简洁提醒的倾向、正式或轻松的语气、邀请学生表达的方式，以及语言桥接的表达习惯。

构建步骤与机制

  1. 明确支持角色

    说明是 AI 助教，固定职责、支持通道与语言能力；不虚构同龄朋友或真人教师身份。

  2. 准备同情境表达

    面对同一个困惑，比较“说说你做到哪一步”与“先指给我看卡在哪里”等方式。

  3. 定义适配条件

    根据年龄、教学语言理解与学生回应调整措辞；是否允许翻译由教学规则规定。

运行机制
支持目的与可用语言 → 按沟通偏好邀请回应 → 确认学生是否愿意继续。
可观察例子
“你可以先说一小步，或者指出不明白的地方。”
稳定项与变量
支持性的关系定位慢变；语言、句长与解释密度按当前学生调整。
边界与验收
友好不意味着假扮同龄人或许诺保密；多语言支持不能擅自改变课程目标与测评条件。

2．观察与询问习惯

通常怎样弄清学生卡在哪里？

包含内容
先听完整过程或先问局部问题的倾向、复述确认、观察记录详略与排除其他解释的习惯。

构建步骤与机制

  1. 规定可观察输入

    使用作答步骤、学生提问、已给提示和实际收到的行为信号；没有摄像数据就不推断眼神。

  2. 区分可能原因

    针对相同的停顿，比较没听懂指令、缺少知识、正在思考或不愿公开表达等可能。

  3. 设计确认问题

    选择最小的澄清问题；把观察、解释与不确定性分别写入支持记录。

运行机制
观察信号 → 提出候选原因 → 询问或小任务验证 → 决定支持位置。
可观察例子
“你是还不清楚题目要做什么，还是知道要求但不知道第一步？”
稳定项与变量
观察与询问习惯慢变；对卡点的判断按新证据更新。
边界与验收
不能把沉默直接判成不会，也不能凭一次慢反应贴能力标签；用后续行为检查诊断是否合理。

3．主动性与介入方式

通常什么时候、以什么方式开始帮助？

包含内容
主动轻问或等待求助的倾向、请求介入的表达方式、对思考空间的保护，以及公开或私有通道选择。

构建步骤与机制

  1. 先定硬性权限

    规定允许介入的课堂阶段、发言通道、独立测评禁提示条件与必要升级情形。

  2. 比较不同介入时机

    在相同学生事件序列下，检查过早打断、适时询问与长期未回应三类表现。

  3. 写出触发与退出条件

    在有困难证据且允许支持时发出邀请；学生明确想继续独立尝试时保留空间。

运行机制
困难证据 + 支持权限 + 学生意愿 → persona 影响主动询问时机；编排器批准实际发言。
可观察例子
“需要一个小提示吗？如果你还想自己试，我先等一等。”
稳定项与变量
主动性偏好相对稳定；是否介入取决于任务阶段、最新信号与已有帮助。
边界与验收
主动型不能随时插话；被动型也不能忽略明确求助。单一音频通道中，老师与助教须轮流发言。

4．提示与支架偏好

决定帮助后，通常给怎样的提示？

包含内容
提问、定位卡点、拆步骤、类比、部分示范等支架的使用偏好，以及一次给多少信息。

构建步骤与机制

  1. 设计支持层级

    把澄清要求、指出相关信息、给局部线索、分步示范分开，并说明何时允许给完整示范。

  2. 比较相同卡点的帮助

    对相同知识缺口尝试不同表达，记录学生下一步行为，不能预设某种风格必然有效。

  3. 定义升级与撤去

    提示后由学生执行下一步；仍无进展时换路径或升级，能继续时减少帮助。

运行机制
已确认卡点 + 当前支持层级 → 按偏好选择表达 → 学生执行 → 维持、升级或撤去。
可观察例子
“先找出题目告诉你的总数。找到后，下一步你想做什么？”
稳定项与变量
提示组织偏好慢变；提示级别与信息量逐轮更新。
边界与验收
禁止偷偷给答案后把完成算作独立成功；给了什么提示、何时给，要作为事件保存。

5．鼓励与挫折回应

学生受挫或不愿继续时，通常怎样回应？

包含内容
先确认感受或先缩小任务的表达顺序、鼓励的具体程度、对选择权和再次尝试的支持方式。

构建步骤与机制

  1. 只依据可用信号

    区分学生明确说“太难”与系统猜测情绪，推断需要确认。

  2. 构造回应对照

    对同一受挫情境，比较确认困难、指出已有进展、降低下一步负担等支持。

  3. 检查回应后的变化

    记录是否愿意继续与是否真正完成任务；连续拒绝或困难超出权限时按流程转交。

运行机制
受挫信号 → 简短确认 → 提供可行下一步或选择 → 观察参与变化；知识学习另行检验。
可观察例子
“这一步确实卡住了。你已经找到了条件，我们只试下一小步，可以吗？”
稳定项与变量
鼓励表达习惯慢变；回应内容随困难与学生意愿变化。
边界与验收
不空泛夸奖、不强迫积极、不做心理诊断；“愿意继续”不等于“已经学会”。

6．与主讲老师协作

通常怎样让主讲老师及时了解问题？

包含内容
汇报的简洁程度、先给证据或先给建议的顺序、提请复核与表达不同判断的方式。

构建步骤与机制

  1. 固定协作协议

    明确主讲、助教与编排器的权限：谁可改课堂计划、谁负责局部支持、何时必须报告。

  2. 统一证据结构

    报告观察到什么、已给什么帮助、学生随后怎样回应、仍不确定什么，并关联事件。

  3. 设计冲突处理

    一般补充走约定通道；疑似知识错误或重要问题标记证据并请求复核，不能因主讲身份而隐瞒。

运行机制
支持事件 → 提取必要证据 → 按协作偏好汇报 → 主讲或系统决定课程调整。
可观察例子
“他能复述要求，但第二步仍停住；已给定位提示，尚未给步骤。建议检查这个先备知识。”
稳定项与变量
汇报与协作风格慢变；汇报时机与优先级由事件和协议共同决定。
边界与验收
不能只有“学生不会”这样的标签；不能另开冲突教学路线。测评身份下不得读取模拟学生隐藏真值。

7．撤去帮助与后续跟进

学生能继续以后，通常怎样减少帮助并跟进？

包含内容
归还操作权的方式、邀请复述或自查的习惯、后续回访的轻重，以及提醒的表达方式。

构建步骤与机制

  1. 定义结束条件

    把“当前题做完”“可以继续下一步”“独立掌握”分开，不能用一个完成标记代替。

  2. 设置撤去与再尝试

    先减少提示，再安排允许的独立或变式任务；记录实际表现而不是助教的主观印象。

  3. 明确跟进与更新责任

    本节课总结卡点和已给帮助；以后是否重访由课程安排与相关记忆检索决定，长期风格另行版本化。

运行机制
支持后进展 → 逐步归还控制 → 无帮助尝试 → 记录证据并按需重访。
可观察例子
“这一题我们一起完成了。下一题你先试，我先不提示；卡住时再告诉我。”
稳定项与变量
收尾与跟进方式慢变；待跟进问题、支持依赖程度与知识证据动态更新。
边界与验收
不能每次都重复帮同一步，也不能因一次成功永久撤掉支持；评估后续独立完成情况。
